#+title: Madshare
#+author: Kian Seibel

* Madshare
Concept doc for a federated audio service (primarily for music)
** server side
- The server should store audio files on a server disk, optionally with S3.
- Audio files and their metadata should be separated.
- The server lets users upload, download and play audio files, with and without decoding (using ffmpeg).
- The server has one admin account.
- The server has user accounts.
- A user cannot upload new audio files without admin permission.
- By default, the server should not allow unauthorized users to download or play a media file, to prevent legal attacks.
- Each media file has a flag whether it may be played/downloaded by unauthorized guests (for open / non-copyrighted music). This is just an access grant to the "anonymous public" principal; the default is deny.
- Each media file may also store a /license/ as metadata (a controlled vocabulary / SPDX-style code, e.g. CC0, CC-BY, public-domain, all-rights-reserved, unknown), distinct from the guest-playable flag.
- The admin may opt in to a policy that auto-derives the guest-playable flag from the license (e.g. auto-publish anything licensed CC0 or public-domain). Caveats: the license read from uploaded file tags is unverified, so the admin opts in and owns the legal risk; auto-derivation only ever /grants/ for a recognized-free allowlist; an unknown or missing license stays private; a manual override always wins.
- The server can connect with other servers via a federation protocol.
- To prevent any legal issues, servers can connect to each other only through a trust system: two admins exchange their keys to connect. But every server has full access to all of its friends' networks (madnetwork).
- An admin may share their library with the madnetwork — all federated servers.
- An admin may share their library only with their friends — servers they trust.
- An admin may choose not to share their library at all.
- Connected servers can download and upload audio files to each other. Each audio file is verified by its hash sum.
- Connected servers can act as balancers for streaming music files if they have the same audio files.
- Servers can block spam servers whose files are scams (untrusted servers). Each admin approves or disapproves the media files they can see in the madnetwork. If a server has a critical mass of untrusted media, its files get a low rating and clients don't see that media. This prevents spam attacks on the madnetwork.

Manually blacklist servers without any rating system. Share information about whom the spam server is friended with, to block them too? I should think about this.
*** AI features
- Recommendation functionality
- Search for music by humming
** client side
- The client should let users discover audio files on the server.
- The client should let users discover audio files on the server's friends and the madnetwork.
- The client should let users play audio files.
- The client should let users download audio files.
- The client should let users upload audio files.
*** Desktop/Mobile client
- The client should work both as a server (able to connect to external servers and share its library) and as a local music player app.
